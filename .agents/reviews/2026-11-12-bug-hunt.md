# zuutf bug hunt, 2026-11-12

Commit `7ec8d2b`. Hunters: 3 on fable, run one at a time. Slices: (1)
the R layer; (2) UTF validation, conversion and detection in C; (3)
Base64, the size limits and the C table `zuutf_api_v1`. Coordinator on
opus. Built here: macOS x86-64 (Intel), R 4.6, simdutf 9.2.1 with the
haswell, westmere and fallback kernels.
Unverified: icelake (AVX-512), ARM NEON, Windows, big-endian hosts, and
the success side of the `INT_MAX` edges (5-6 GB each, past this
machine's 8 GB).

The target map was taken from `.agents/assurance.md` (#69). The
weakest rows were: hand-vector oracles (marked-encoding input, the BOM
rules, replacement outside UTF-8), the limit gaps #67 and #68, and the
missing mutation (#65) and reach floor (#66).

## 1. Keep a leading U+FEFF in character input — #70, high, reproduced

- Where: [zut_convert.c:228](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_convert.c#L228),
  [zut_validate.c:42](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_validate.c#L42),
  [zut_count.c:36](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_count.c#L36).
- Trigger: `utf_encode("﻿abc", "UTF-8")` gives `61 62 63`.
  `utf_count()` gives 3 where `nchar()` gives 4. `utf_error_at()`
  reports 2 for `EF BB BF 61 FF` marked UTF-8; byte 5 is the bad one.
- Cause: `zut_strip_bom()` runs on character elements, where U+FEFF is
  text, not a byte-order mark.
- Fix: strip it only for raw input (design §6 names only `utf_decode()`
  and `utf_convert()`, with a matching `from`).
- Family: 1. Siblings checked: `utf_valid()`, `utf_error_at()` and
  `utf_length_as()` share it; `base64_encode()` does not strip.
- Test the suite lacked: `utf_encode()` against `iconv(toRaw = TRUE)`
  and `utf_count()` against `nchar()` on strings with U+FEFF first.
- Found by hunters 1 and 2 independently.

## 2. One U+FFFD for a trailing high surrogate and an odd byte — #71, medium, reproduced

- Where: [zut_convert.c:113-119](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_convert.c#L113-L119).
- Trigger: `utf_convert(as.raw(c(0x41,0,0,0xd8,0xd8)), "UTF-16LE",
  "UTF-8", invalid = "replace")` gives `41 ef bf bd ef bf bd`. Python
  and Node's `TextDecoder` give one U+FFFD. Same under every kernel.
- Cause: the partial-unit replacement is added after the trailing
  surrogate has already been replaced.
- Fix: one replacement for both when the last whole unit is a high
  surrogate. Fix the roxygen sentence that promises both rules.
- Family: 4. Siblings checked: UTF-32 and UTF-8 ends match their
  oracles. This was the only mismatch in about 14,000 cases × 6 targets.
- Test the suite lacked: UTF-16 "replace" against Python or Node, on
  every combination of trailing surrogate and odd byte.

## 3. Native strings escaped by `enc2utf8()` in a C locale — #72, medium, reproduced

- Where: [R/input.R:38](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/R/input.R#L38),
  [R/base64.R:145](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/R/base64.R#L145).
- Trigger: under `LC_ALL=C`, `utf_count()` of the unmarked UTF-8
  bytes of "cé" is 9, `base64_encode()` encodes the text `c<c3><a9>`,
  and `utf_valid("\xe9")` is TRUE.
- Cause: design §5 sends native strings through `enc2utf8()`, which
  writes `<xx>` escapes in a C locale. The design does not consider
  this case.
- Fix: a design decision, between refusing, reading the bytes, and
  documenting. Options are in the issue.
- Family: none (see Cross-cutting).
- Test the suite lacked: the native-string tests rerun under
  `LC_ALL=C` and a Latin-1 locale.
- Found by hunters 1 and 3 independently.

## 5. `%d` with a double index in `raise_status()` — #74, low, reproduced via `:::`

- Where: [R/convert.R:224-253](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/R/convert.R#L224-L253).
- Trigger: an index above 2^31 gives a `simpleError` from `sprintf()`,
  not a `zuutf_error`. It needs a list of more than 2^31 elements to
  reach from an exported function.
- Family: 1 (`as_count()` returns an integer or a double).
- Test the suite lacked: `raise_status()` with an index of 2^31 + 5.

## 6. Base64 `offset` is not the first offending character — #75, low, reproduced

- Where: [zut_base64.c:38-43](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_base64.c#L38-L43),

  [:129-137](https://github.com/pedrobtz/zuutf/blob/7ec8d2be761c498f67e4ca572fe200d48d703823/src/zut_base64.c#L129-L137).

## Cross-cutting

- **U+FEFF is the meeting point of three findings' worth of shape.** A
  rule written for bytes (skip a matching BOM) was applied to text.
  Wherever a helper is shared between byte input and character input,
  check that each rule belongs to both.
- **Candidate rule for `correctness.md`, not one of the four
  families:** *a conversion R performs on the package's behalf can change
  the data silently.* `enc2utf8()` escapes in a C locale, `sprintf("%d")`
  refuses a double, and `format()` rounds. Every R-side conversion of user
  data either checks its result or refuses the inputs it cannot carry.
  The test is the same suite rerun in a hostile session: `LC_ALL=C`, a
  Latin-1 locale, `OutDec`, `scipen`.
- Every wrong-result bug was in an edge case of an oracle-backed
  boundary, not in the main path: the well-formed conversions matched
  `iconv()` and Python byte for byte under every kernel, and Base64
  matched RFC 4648 and WHATWG oracles on 3.3 million cases.

## Held: what was probed and stood

- Well-formed conversion in all 25 UTF pairs, and Latin-1 in both
  directions, against `iconv()` (1,500 strings) and Python (about
  14,000 cases × 6 targets), under haswell, westmere and fallback.
- Validation, error offsets, counts and `utf_length_as()` against a
  scalar oracle. Each ill-formed sequence was placed at every offset
  0..150 across the 16/32/64-byte block edges.
- Maximal-subpart replacement for UTF-8, and the "na" and "error"
  policies, with the NUL rule of design §6.
- "auto" against the name `utf_detect()` returns, on 20,000 inputs.
  "UTF-16"/"UTF-32" with a BOM against the concrete names. BOMs cut
  short at every length.
- Switching kernels at run time, and scratch reuse between a large call
  and a small one.
- Base64 decoding: 3.3 million cases over 9 modes against WHATWG and
  RFC 4648 oracles (the WHATWG oracle was itself checked against Node's
  `atob()`). Encoding: 16,444 cases including `line_length` edges.
- The rejecting side of every size limit: Base64 over `INT_MAX`,
  `utf_decode()` over 2^31 - 1 bytes, and offsets across the
  integer/double switch at 2^31.
- Every member of the C table `zuutf_api_v1`, at capacities of need - 1,
  need and need + 1, with canary bytes after every buffer: no overrun.
- Argument validation for every exported argument (NA, NULL, length 0
  and 2, wrong types, fractions, Inf, 2^31, 2^53). Results unchanged
  under `OutDec = ","`, `scipen = -5`, `digits = 3`, `warn = 2` and
  a non-UTC TZ.

## Not reached

- The success side of the `INT_MAX` edges (5-6 GB each); #67 and #68
  ask for a lowerable limit so the edge can be straddled.
- The `R_XLEN_T_MAX` branch for raw output: unreachable.
- The icelake and NEON kernels, Windows, and big-endian hosts.
- User interrupts inside the loops; the C table from non-R threads.

## Not reproduced, and by design

- A run of surplus `=` reports the first `=`: design §6 ("the first
  `=` of the run"). Hunter 1 reported it; it is by design.
- "auto" reads `41 00` as UTF-8 and fails on the NUL, and `FF FE 00 00`
  is a UTF-32LE BOM: design §5 and §6, documented in `utf_detect()`.
- A BOM of the other byte order is kept as data: design §6 ("matches
  `from`").
- `utf_length_as(to = "Latin-1")` counts code points the conversion
  refuses: documented in R/count.R.
- Strict decoding refuses the package's own line-wrapped output:
  documented (whitespace is an error in strict mode).
